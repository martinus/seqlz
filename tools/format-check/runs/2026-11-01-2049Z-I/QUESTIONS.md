# Places where format.md can be read two ways

Written from `format.md` only. Each entry quotes the place, gives the readings and says which one
the rest of format.md supports, where it does.

| ID | section | quoted | reading A | reading B | notes |
| --- | --- | --- | --- | --- | --- |
| Q1 | Notation | "`read(3)` of the bits 0, 1, 1 is the number 6; the same bits as a code are the bit string `011`." | The bits are listed in the order they are read; then `read(3)` = 3, and "6" is a mistake. | The list "0, 1, 1" is in some other order (e.g. least significant first, or bits 0, 1, 2 of a number), and `read(3)` = 6. | `read()` is "the first bit read is the most significant one", and the example (`read(12)` = 1010 from `001111110010`) uses reading A. So the sentence is wrong, but a reader who trusts it would read every `read()` backwards. |
| Q2 | The tables / Example | "`ML` \| `LEN_SYMBOLS` \| 8 bits" and "`1111111` \| `symbol(ML)` = 23" | The table is right: `ML` has 8-bit codes, and the example's bits for `ML` are wrong. | The example is right: symbol 23 has the 7-bit code of only ones, so `ML`'s longest code is 7 bits and the table's "8 bits" is wrong. | Both can't hold for a complete canonical code (CLAIMS C61). A decoder that sizes its lookup by "8 bits" works either way; one that trusts the example would decode wrongly if A is the truth. |
| Q3 | Layout | "with coded literals `len < 3 + w + e`, `dt` is not 1, 2 or 3, ..." | The `dt` check applies only with `e = 1`, where there is a `dt` byte. | `dt` means byte 3 always, and must be 1 to 3 in every coded block. | The layout table says "with `e = 1` the byte `dt` ..., else nothing", so A. B would forbid many valid size bytes. |
| Q4 | Layout | "with coded literals `len < 3 + w + e`" | With `len = 2` and bit 15 of `h` set, `t` doesn't exist, and the block is invalid because nothing can be read. | `t` is read as 0 past the end (as `B` may be), so `w = 5`, `e = 0`, and the block is invalid because `2 < 8`. | Same result, invalid, under both. Only the rule that rejects it differs. The same goes for `len = 3` with `e = 1`. |
| Q5 | Offsets | "For a sequence with a match, an offset of 0, or one larger than the bytes written so far, makes the block invalid." | "so far" = after the sequence's literals are copied (`off > \|out\|` after `copy(ll)`). | "so far" = at the start of the sequence, before its literals. | The pseudo-code and "the first match's offset is at most that sequence's `ll`" say A. Under B the first match could never be valid. |
| Q6 | Literals as deltas | "`dt = 3`: `x` the smallest multiple of `last` ..., where `last` is the offset of the sequence before, 1 for the first" | `last` is the offset of the previous sequence (the pseudo-code sets `last = off` only after `copy(ll)`). | `last` is the offset of the sequence the literals belong to, which is read from `B` before the literals are copied. | The words and the pseudo-code say A. A decoder that sets `last` when it reads the offset gets B and other bytes. |
| Q7 | Literals as deltas | "`out[p - x]` is a byte already written, ... as it is in the block." | The decoded byte (after the delta was added back), "the block" being the uncompressed block. | The byte as it is stored in the compressed block, i.e. the stored delta of that earlier literal. | "`copy()` writes `(stored + out[p - x]) mod 256`", and `out` is the block being written, so A. "in the block" could still make someone think of the compressed block. |
| Q8 | Literals as deltas | "Take a literal that `copy()` writes to byte `p` of the block ... If `p >= x`" | `p` counts from 0, `p = \|out\|` before the byte is written. | `p` counts from 1. | `out[p - x]` and "byte 0 and 1" of the header suggest 0-based. With B, every test `p >= x` would move by one. |
| Q9 | A block's own literal table | "symbol `9 + k` ...: the next `2^(k-1) + x` byte values have no code" and "The block is invalid if ... a byte value with a code is above 255, ... or `3 + w + e + d > len`" | A skip that goes past byte value 255 is fine in itself, and the block is invalid only when a length follows. The list must end with a length, so this always happens. | A skip that goes past 255 is itself invalid. | Same set of valid blocks. But a decoder that reads zeros past the end (as allowed for `B`) and follows A can loop forever if `OWN`'s code of only zeros is a skip; and `d` is only defined once the list ends, so "`3 + w + e + d > len`" says nothing about a description that never ends. Readings: the decoder must stop at `len` / at byte value > 255, or the rule doesn't say. |
| Q10 | A block's own literal table | "then `x = read(k - 1)`" | `read()` here reads the next bits of the description (the table's bits, most significant first). | `read()` is the function defined for `B` and reads from `B`. | `read()` is defined in "The bitstream of the sequences" as reading from `B`. The context says A. |
| Q11 | Literals as deltas | "`out[p - x]` is a byte already written, of the match before or a literal of the same sequence, as it is in the block." | A description (and not always true): `p − x` may be anywhere before `p`. | A rule: a block where `out[p − x]` lies in an earlier sequence is invalid, or such literals are stored as they are. | No such rule is in the list of invalid blocks, and "If `p >= x`" is the only test, so A. The sentence is false in general (CLAIMS C49). |
| Q12 | No version in the block | "The values of byte 2 with a code above 8, and the values of `dt` other than 1 to 3, are invalid now" | Only in blocks with coded literals, where byte 2 is `t`. | In every block, so a raw block whose first literal has low nibble 9 to 15 is invalid. | The layout says A (in a raw block byte 2 is a literal). Under B, raw blocks would lose 7/16 of their first byte values. |
| Q13 | Coded literals | "they take at most `8 * s[j]` bits and fewer than 8 less" | "fewer than 8 bits less than `8 * s[j]`": `8 s[j] − 8 < bits ≤ 8 s[j]`. | "fewer than 8 less" = at most 8 bits less: `8 s[j] − 8 ≤ bits`, allowing a whole byte of padding. | "must end in its last byte" says A. |
| Q14 | The tables | "literal tables 0 to 7 \| 256 each \| 10 bits" | Each of the 8 tables has a longest code of exactly 10 bits. | 10 bits is the longest over all 8; some tables may have shorter longest codes. | Matters only for a checker of the table column; decoding is the same. |
| Q15 | The tables | "The SHA-256 of each table's lengths, as bytes in symbol order (the literal tables one after the other)" | The literal tables in the order 0 to 7, as `code` numbers them. | Some other order (e.g. the order of `seqlz_lit_sets[]`, if that differed from `code`). | Probably the same; not said. |
| Q16 | Prefix codes / The tables | "Every table is **complete**" | A statement about the fixed tables, and, through "The list ends as soon as the codes fill the code space", about own tables. | Also a rule a decoder must check on the fixed tables it has. | The hashes are given for checking the tables; completeness itself is not called a validity rule of blocks. |
| Q17 | The bitstream of the sequences | "A decoder may read zeros past the end instead of checking at every read, and check at the end that it did not use them" | "did not use them" = no bit read past `len` went into a code or a `read()`. | Also: no bit after the last needed bit at all, which is the padding rule. | Together with "fewer than 8 bits ... are left ... and they are 0" both give the same result. Only the order of the checks differs. |
| Q18 | Coded literals | "A decoder may read past the end of a stream, as long as it checks this." | It reads the real bytes after the stream (the next stream, the table or `B`) and then checks where the codes ended. | It reads zeros past the stream's end. | Same result if the check is made; the bytes a decoder sees past the end differ. |
| Q19 | Example / Status | "with the 4 KiB tables" | A leftover from the time of 16 KiB tables; there is one set of tables. | There are other tables, for other block sizes, that a decoder may need. | Status says "There is no format for blocks of 16 KiB", so A. |
| Q20 | The idea | "*Why:* a block of 4 KiB is too small to carry tables of its own." | About `TOK`, `LL` and `ML` only. | About all tables, which "A block's own literal table" then contradicts. | It is a *Why:*, not part of the format. |
| Q21 | Status | "This is the format of 21st October 2026" | The format of the 4 KiB blocks has not changed since 21 October; on 1 November only the 16 KiB part was removed. | The file describes the format as of 21 October, and later changes (1 November) are not in it. | The text was changed on 1 November ("Until 1st November 2026 this file also had blocks of 16 KiB"), so A is likely. |
| Q22 | What the compressor writes (not part of the format) | "with the `dt` whose deltas take the fewest bits in the best fixed table, counted for every 11th literal of the block, with `dt`'s 8 bits scaled the same way, as 1, where that is not `e = 0` and the deltas get coded" | `dt`'s 8 bits count as 8/11 ≈ 1 bit in the sample; "where that is not `e = 0`" = where deltas are better than no deltas. | `dt` is counted as 1 byte, or as the value 1; "that" means the chosen `dt`, compared some other way. | Not part of the format; matters only for writing the same bytes as `seqlz_compress()`. |
| Q23 | What the compressor writes (not part of the format) | "else the class with the fewest offset bits that holds it" | Fewest offset bits only (the table's column). | Fewest bits in all, the token's code included, which depends on the class. | A is what the words say. |
| Q24 | Decoding | "`copy(k)` appends the next `k` literals ... with raw literals and with `e = 0` as they are" | Raw literals are never deltas (`e` exists only in coded blocks). | Raw blocks take `e` from somewhere (byte 2 is a literal there). | A; there is no `e` in a raw block. |
